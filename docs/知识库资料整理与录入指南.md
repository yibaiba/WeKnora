# 知识库资料整理与录入指南

> 适用对象：资料提供人、知识库录入人员和知识库管理员。  
> 目标：让资料能够被稳定解析、准确检索，并在需要时生成高质量的 Wiki 页面。

## 1. 先分清两个概念

WeKnora 中需要判断的不是“这个文件是不是 Wiki”，而是下面两件事。

### 1.1 知识库类型

| 类型 | 用途 | 适合资料 |
| --- | --- | --- |
| 文档库 | 保留原文，通过文档分块进行检索和问答 | PDF、Word、PPT、Markdown、网页、表格等 |
| 问答库 | 按“标准问题 + 标准答案”精确管理 | 客服 FAQ、制度问答、产品问答和故障问答 |

知识库创建后类型不能直接切换。录入前应先确认资料是“原始文档”还是“已整理的问答对”。

### 1.2 文档库的处理方式

| 处理方式 | 作用 | 适合场景 |
| --- | --- | --- |
| RAG 检索 | 对原文分块、向量化并建立关键词索引 | 查找原文、引用条款、追溯资料来源 |
| Wiki | 从文档中提取实体和概念，生成相互关联的知识页面 | 按人物、产品、项目、系统或概念浏览多份关联资料 |

**Wiki 是文档库的一项索引能力，不是一种文件类型。RAG 和 Wiki 可以同时开启。**

## 2. 如何选择录入方式

### 第一问：资料是否已整理成一问一答？

- 是：录入**问答库**。
- 否：一般录入**文档库**。

### 第二问：用户是需要查原文，还是需要浏览知识体系？

- 查制度原文、合同条款、产品参数或报告数据：开启 **RAG 检索**。
- 按人物、项目、产品、系统、流程或概念查看关联资料：另外开启 **Wiki**。
- 两种需求都有：同时开启 **RAG + Wiki**。

### 第三问：这份资料是否值得长期保留？

- 当前有效、来源可靠、有明确负责人：可以录入。
- 已过期、无法确认版本、内容重复或只用于临时传递：先整理，不要直接录入。

### 常见资料分类表

| 资料 | 建议类型 | 建议能力 | 说明 |
| --- | --- | --- | --- |
| 公司规章制度 | 文档库 | RAG + Wiki | 既要引用原文，又要串联部门、职责和流程 |
| 产品手册、技术文档 | 文档库 | RAG + Wiki | 适合按产品、版本、模块和术语建立关联 |
| 合同、法律文件 | 文档库 | RAG | 优先准确引用原文，不用 Wiki 页面替代法定文本 |
| 项目立项、方案、会议纪要 | 文档库 | RAG + Wiki | 适合串联项目、成员、里程碑和决策 |
| 临时通知 | 文档库 | RAG | 标明生效和失效时间，到期及时下架 |
| 客服标准话术 | 问答库 | FAQ | 一个标准问题对应明确答案 |
| 故障处理资料 | 问答库或文档库 | FAQ 或 RAG | 简短且答案唯一用 FAQ；复杂排障流程用文档 |
| 统计报表、台账 | 文档库 | RAG | 保持标准表格结构，不建议主要依赖 Wiki |
| 个人草稿、聊天截图 | 暂不录入 | - | 先由负责人确认并整理成正式资料 |

## 3. 通用整理规范

### 3.1 只保留一个有效版本

- 不要同时上传“最终版”“最终版 2”和“最终修订版”。
- 保留已生效的最新版本，历史版本放入档案区或独立知识库。
- 新版本导入后，下架或删除被替代的旧版本。

### 3.2 使用能说明内容的文件名

建议命名：“主题_部门或产品_版本或生效日期”。

正确示例：

- 员工差旅管理办法_人力资源部_V3_2026-07-01.pdf
- CRM系统操作手册_销售中心_V2.1.docx
- 客服常见问题_智能终端_2026Q3.xlsx

不合格示例：

- 新建文档.docx
- 扫描001.pdf
- 最终版-真的最终版.pdf
- 微信图片_20260701.jpg

### 3.3 让文档层级清楚

- 使用唯一、明确的文档标题。
- 使用一级、二级、三级标题，不要只靠放大字号或加粗表示标题。
- 每个章节只讲一个主题，步骤使用有序列表。
- 明确步骤的前置条件、执行人和预期结果。
- 专有名词前后一致，首次出现时写全称和简称。
- 避免“如上”“按以前方式”“这个”等脱离上下文就无法理解的表达。

### 3.4 在正文中写清关键信息

正式文档首页建议包含：

| 字段 | 示例 |
| --- | --- |
| 文档名称 | 员工差旅管理办法 |
| 文档编号 | HR-POL-012 |
| 责任部门/负责人 | 人力资源部/张三 |
| 版本 | V3.0 |
| 生效日期 | 2026-07-01 |
| 适用范围 | 公司全体员工 |
| 保密级别 | 内部公开 |
| 废止或替代关系 | 替代 V2.0 |

### 3.5 按业务边界分库

正确示例：“人力资源制度库”“CRM 产品知识库”“客服标准问答库”。

不建议按“PDF 文件库”“Word 文件库”或“2026 年所有资料”分库。不同保密级别和权限范围的资料应分开建库或分别授权。

## 4. 不同文件的整理方法

### 4.1 Word、Markdown 和网页文本

- 使用真实的标题样式，不要用空格和换行模拟排版。
- 不要把重要文字只放在文本框、页眉、页脚或流程图截图中。
- 删除修订痕迹、批注、隐藏文字和无关模板说明。

### 4.2 PDF

- 优先上传可选中、可复制文字的 PDF。
- 扫描 PDF 应方向正确、页面完整、无黑边和遮挡。
- 复杂表格、多栏排版、手写体和印章遮挡会降低解析质量，导入后必须抽查。
- 原始 Word 与正式 PDF 内容一致时，可优先导入结构更清晰的版本，但不要重复导入。

### 4.3 Excel 和 CSV

- 第一行使用唯一且明确的列名。
- 一行表示一条记录，一列表示一种固定属性。
- 表头不要合并单元格，数据区不要插入空行、小计标题或无关说明。
- 同一列使用相同数据格式，日期统一为 YYYY-MM-DD。
- 不要依赖颜色、底纹或单元格位置表达含义，应设置显式字段。
- 删除空工作表、隐藏行列和无关的辅助计算区。
- 说明指标口径、单位、时间范围和数据来源。

### 4.4 PPT

- 每页有明确的页标题，不要只放图片而无文字说明。
- 图表结论应写在正文中，不要只在演讲时口头补充。
- 删除过场页、纯装饰页和大量重复的介绍页。

### 4.5 图片和扫描件

- 保持背景干净、无反光、文字方向正确且字号可辨认。
- 一张图尽量只包含一页资料，不要将多张截图拼成长图。
- 屏幕截图中的关键内容应补充为文字，聊天截图不应直接作为正式知识来源。
- 图片解析依赖 OCR 或视觉模型，导入后必须检查识别结果。

### 4.6 音频

- 保持无明显噪声、人声清晰，避免多人同时说话。
- 录入前确认已获得必要的录音和使用授权。
- 音频解析依赖 ASR 模型，人名、产品名和数字需要人工校对。
- 当前不支持直接上传视频文件。

## 5. FAQ 问答资料规范

FAQ 库适合“问题边界明确、答案相对稳定”的内容。不要把一篇长文档按段落机械拆成大量问答。

### 5.1 每条 FAQ 应包含

- **标签**：产品、模块或业务分类。
- **标准问题**：只表达一个意图。
- **机器人回答**：结论明确，必要时包含条件、步骤和限制。
- **相似问题**：用户的其他常用问法，但语义必须一致。
- **反例问题**：用词相似，但不应命中该答案的问题。

合格示例：

| 字段 | 内容 |
| --- | --- |
| 标签 | 差旅管理 |
| 标准问题 | 出差住宿费的报销上限是多少？ |
| 相似问题 | 出差酒店最多能报多少？ |
| 回答 | 住宿费上限按城市类别和人员级别执行，请查看《员工差旅管理办法》第四章的当前标准。 |

不合格示例：“出差怎么办？”“按公司规定处理。”问题范围过大，答案没有操作价值，也没有指明规则来源。

### 5.2 FAQ 批量导入

系统支持 JSON、CSV 和 Excel 导入。CSV/Excel 建议使用系统界面提示的当前模板，常用表头包括：标签、问题、相似问题、反例问题、机器人回答、是否全部回复、是否停用、是否禁止被推荐。

多个相似问题、反例问题或答案在同一单元格内使用 `##` 分隔。导入前不要自行修改列名。

## 6. 如何整理适合 Wiki 的资料

Wiki 会识别文档中的人物、组织、产品、项目、系统和领域概念。输入资料的命名越稳定、关系越明确，生成的 Wiki 质量越高。

### 6.1 建议做法

- 专有名词第一次出现时使用全称，并在括号中声明简称。
- 同一人物、项目或产品在不同文档中使用相同名称。
- 明确写出关系，例如“A 系统由数字化中心运维”，不要只用并列名单暗示关系。
- 对含义接近的名词给出定义和区别。
- 标明时间范围和版本，避免新旧关系被当成同时有效。
- 为图表、流程图和架构图增加文字说明。

### 6.2 不适合直接开启 Wiki 的资料

- 单份、篇幅很短且没有可关联概念的通知。
- 以数值计算为主的报表或台账。
- 未整理的聊天记录、邮件往来和会议录音转写。
- 大量重复、互相矛盾或版本不明的资料。
- 要求逐字引用、不允许内容归纳的法定文本。

Wiki 页面用于知识组织和浏览，不能替代原始文档作为合同、制度或法律依据。

## 7. 支持格式与环境限制

文档导入接口可接收以下常见格式：

- 文档：PDF、TXT、DOC/DOCX、EPUB、HTML/HTM/MHTML、Markdown。
- 表格和结构化数据：CSV、XLS/XLSX、JSON。
- 演示文稿：PPT/PPTX。
- 图片：PNG、JPG/JPEG、GIF。
- 音频：MP3、WAV、M4A、FLAC、OGG。

具体能否成功解析，还取决于当前部署启用的文档解析引擎、OCR/视觉模型和 ASR 模型。录入人员应以上传界面实际显示的可用格式为准。

## 8. 标准录入流程

### 第一步：确认权属和权限

- 确认资料来源、负责人和可使用范围。
- 确认不包含不应入库的个人隐私、密码、密钥和其他敏感凭据。
- 根据保密级别选择正确的知识库和共享范围。

### 第二步：分类和去重

- 判断应录入文档库还是问答库。
- 检查库内是否已存在相同资料。
- 只保留当前有效版本，先处理内容冲突。

### 第三步：整理内容

- 修正文件名、标题层级和表格结构。
- 补充负责部门、版本、生效日期和适用范围。
- 删除无关页、空白页、修订痕迹和重复内容。

### 第四步：小批量试导入

- 新类型资料先选择 3 至 5 份有代表性的文件。
- 等待解析完成，不要在处理中反复上传同一文件。
- 检查标题、段落、表格、图片文字和音频转写是否正确。

### 第五步：用真实问题验收

准备至少 5 个业务人员真正会问的问题，检查：

- 能否找到正确文档和段落。
- 回答是否与原文一致，引用来源是否正确。
- 旧版本或重复文档是否干扰结果。
- 开启 Wiki 时，主要人物、产品、项目和概念是否被正确识别。

### 第六步：批量导入和记录

- 试导入通过后再批量录入同类资料。
- 记录导入日期、资料范围、负责人和失败文件。
- 对解析失败、内容缺失或分类错误的文件修正后重新导入，不要忽略失败状态。

## 9. 导入前检查清单

- [ ] 已确认资料的负责人和可使用范围。
- [ ] 已选择正确的文档库或问答库。
- [ ] 已由管理员根据业务需求确认 RAG/Wiki 策略。
- [ ] 文件名可以说明主题、版本和日期。
- [ ] 文档标题和章节层级清楚。
- [ ] 已标明版本、生效日期、责任部门和适用范围。
- [ ] 已删除重复、过期和冲突版本。
- [ ] 扫描件、图片和音频质量满足识别要求。
- [ ] 表格的表头、单位、日期和指标口径已统一。
- [ ] 不包含密码、密钥或无权共享的敏感信息。

## 10. 导入后验收清单

- [ ] 文档处理状态是成功，不是处理中或失败。
- [ ] 标题、正文、表格和列表没有明显丢失或乱序。
- [ ] 随机抽查至少 10% 的文件，且不少于 3 份。
- [ ] 用真实问题可以检索到正确内容。
- [ ] 回答中的引用可以追溯到正确原文。
- [ ] Wiki 页面没有大量重复概念、错误合并或明显缺失。
- [ ] 问答库的相似问法能命中，反例问法不会错误命中。
- [ ] 失败文件和错误内容已记录并分派处理。

## 11. 角色和责任

| 角色 | 主要责任 |
| --- | --- |
| 资料提供人 | 保证内容正确、版本有效、来源可追溯 |
| 录入人员 | 按规范整理和分类，执行导入前后检查 |
| 知识库管理员 | 建立知识库、配置 RAG/Wiki、分配权限、处理冲突和定期审查 |
| 业务审核人 | 检查答案与业务规则是否一致，确认内容可正式发布 |

每个知识库应至少指定一名管理员和一名业务审核人，并定期检查过期内容、失败任务和用户无法命中的问题。
